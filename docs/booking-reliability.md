# 挂号与接诊可靠性

## 实施顺序
1. 在隔离 Tomcat / MySQL 用虚构数据复现重复提交、旧号源和 GET 接诊，建立回归基线。
2. 新挂号记录保存时段与按患者隔离的请求标识；保留扣号和建单的同一事务。修复查询等待、旧响应、重试及接诊方法和状态检查。
3. 用两个患者、两位医生验收最后一号并发、同请求重试、写入失败回滚、旧记录、浏览器挂号和接诊权限；不连接现有业务库。

## 迁移与部署
- 独立脚本：`db/migrations/2026-11-25-booking-shift.sql`。适用于使用 InnoDB 的当前 `guahao` 表；**仅在明确选中的目标库执行一次**。脚本不指定库，不重导初始化数据，不回填旧行。此次授权仅限隔离测试库，不能用于现有业务库。
- `booking_shift` 保存新记录的上午或下午；旧行的 `NULL` 显示为「时段未记录」。`booking_request_id` 配合患者账号建立唯一键，避免同请求再次扣号。只有从挂号页面发起的新版提交使用这两个字段；现有其他写入可保持 `NULL`。
- 正式部署需另行授权。先确认目标结构和备份，再执行迁移并重新编译部署 Java (`AppointmentBooking.class` 必须在实际类目录)，然后用隔离数据复核。迁移后仍可回退应用版本并保留新增的可空列；不要为应用回退直接删列，以免丢失班次信息。
- 同一请求标识返回已有预约；另开挂号页面生成新标识，可主动另约。标识随挂号记录保存，不覆盖管理员事后硬删除该记录的场景（不在本次范围）。
